# World state vs planning scene

Two different “maps of the world” exist on purpose:

| | **Semantic world state** | **Geometric planning scene** |
| --- | --- | --- |
| Question | *What* is where (SKU, lane membership, held?, task phase) | *Will the robot hit* something if it moves like this? |
| Authority | Yes: inventory / reservation source of truth | No: derived collision geometry |
| Wrong use | Using MoveIt objects as the stock database | Letting planners invent which can is “lane 3” |

A projector copies *enough geometry* from world state (+ obstacles) into MoveIt under leases,
then verifies reconciliation. Perception may keep updating **evidence** during a reservation,
but attachment and new lane membership require token-bearing commits. Accepted lane surveys
can also reconcile FIFO sales and remove contents through world-state rules. For the reserved
product itself, world state holds the pose across the pre-attach window: a fresh confirm frame
advances freshness but replaces `pose_in_world` only past a **20 mm divergence bound**, which is
then applied immediately. That keeps the staged grasp and the projected obstacle reading one
pose, while a product that really moved is surfaced to the scene instead of hidden behind the
hold.

## Why it matters here

Restocking is transactional: reserve → grasp → attach → insert → commit → verify. If MoveIt
were the database, a collision-object rename would corrupt inventory. Failures also split:
“planning scene drifted” and “inventory wrong” are different incidents.
